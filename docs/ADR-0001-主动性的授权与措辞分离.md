## 背景

BDP 特性要让一个被动 harness 具备主动性。技术上存在两种做法：

- **方案 A（模型自治）**：把行为事件流水交给模型，由模型决定「此刻要不要说话、说什么」。
- **方案 B（代码授权 + 模型措辞）**：代码侧状态机决定「该不该开口」，仅在放行后才调用模型生成话术。

## 决策

**采用方案 B。模型不得自行决定是否主动开口。**

```
行为采集 → 状态机（纯函数） → 闸门 ──放行──> 状态行(≤120字符) → 模型生成话术
                                │
                                └──否决──> 静默（不调用模型）
```

## 理由

1. **论文证据**：*Proactive Agent*（Lu 等，ICLR 2025）明确结论——闭源模型**倾向于过度主动，在用户不需要帮助时无法保持沉默，误报率高**。本项目使用 Agnes（闭源），直接命中此缺陷。
2. **可测试性**：状态机是纯函数 `(events, prev) → state`，可单测、可回放、可 A/B。模型自治方案无法写断言，只能靠感觉调 prompt，必然玄学化。
3. **可解释性**：看板能显示「这位访客当前姿态 = ENGAGED，已开口 1/2」，主人能看懂并干预；模型自治是黑盒。
4. **成本与延迟**：闸门否决时不调用模型，省一次 API 调用；也避免了 F2（上下文膨胀导致首字变慢）。
5. **降级**：模型超时或出错时，仍能按姿态输出 `resume.json` 里的规则兜底话术。

## 代价（接受）

- 需要维护一份状态机代码与姿态定义，比纯 prompt 方案多工作量。
- 灵活性下降：模型无法「灵光一现」地在未授权时机说话。**这是有意为之**——本产品是替人打招呼，宁可保守。

## 复核条件

出现以下任一情况应重新评估本决策：

- 评测集（10 场景）显示误报率持续 > 30% 且归因于闸门规则过松/过紧而非模型；
- 换用可微调的开源模型（此时可借鉴 ProactiveBench 思路做主动能力微调）；
- 产品目标从「招聘打招呼」变为其他场景（主动性的最优保守度不同）。
